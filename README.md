> Execution sandboxes, browser environments, and isolation runtimes for AI agents.

46 projects · Upstream documentation checked 2026-09-30. Curated by [agentlist.io](https://www.agentlist.io).

**Give your agent a place to work, with boundaries you can inspect.**

Before leaving an agent to run code, decide which files, networks, and credentials it needs. Then decide what should survive the task. This list helps you compare execution environments and their building blocks; the word sandbox alone does not establish an isolation guarantee.

Environments for running agent tools or untrusted code, plus the isolation runtimes used to build them. Browser automation libraries alone are excluded. A listing is not a security certification.

## How to choose

- Works with: Can your agent run the required commands, language runtimes, browser, and tools in this environment?
- Runs where: Is execution on your machine, your infrastructure, or a hosted service? What isolation mechanism is documented?
- Needs access to: How are filesystem mounts, outbound networking, and credentials restricted? What must you configure yourself?
- Keeps what: Are files ephemeral or persistent? Can you snapshot, resume, export, and clean up an environment?
- Human involvement: Can you inspect work, interrupt execution, and require approval before consequential actions?
- Main limitation: Which workloads or threats fall outside the documented boundary? Check startup behavior, resource limits, and persistence against your task.

Use these questions to narrow your shortlist. An entry’s source link records the documentation used for its description; it does not mean every question above has been answered or tested. Treat undocumented capabilities as unknown, and confirm requirements against the linked project before adopting it.

## Agent execution platforms

- [Cloudflare Sandbox SDK](https://github.com/cloudflare/sandbox-sdk) - SDK that adds file copy, S3 mounts, and directory backup to a Cloudflare Container your own Worker Durable Object starts. The README says the Worker picks the sandbox, whether internet is enabled, and which hosts it may reach, while bucket credentials stay in the Worker because it signs storage requests; a directory backup can be restored into another container. Version 1.0 no longer runs commands for you, and this list did not deploy a Worker. **Cloud platform SDK.**
- [Daytona](https://www.daytona.io/) - Hosted environment for running generated code. The GitHub README, re-read on 2026-09-30, says this public repository is unmaintained and that core development moved to a private codebase in June 2026; the old tree remains public under the license pinned at v0.190.0, without further fixes. The product site was still up on that date, and this entry does not review the private codebase. **Sandbox platform.**
- [Docker Sandboxes](https://docs.docker.com/ai/sandboxes/) - Docker's sbx CLI runs coding agents on your machine or on Docker-managed cloud compute. The docs separate local and cloud credentials, network policy, and lifecycle, and they point to an architecture page for microVM isolation. That architecture page was not re-read for this entry, and sbx was not run. **Local or hosted.**
- [E2B](https://github.com/e2b-dev/E2B) - Cloud service for running generated commands in isolated sandboxes, with JavaScript and Python SDKs that need an API key. The README also documents a Code Interpreter package for runCode and an E2B Desktop SDK for mouse, keyboard, screenshots, and desktop streaming; Desktop is a sibling for computer use, not a second vendor. Self-hosting points at a separate runtime repository and Terraform, but the README does not name the isolation mechanism or a snapshot format, and self-host completeness of the control plane was not tested. **Cloud sandbox.**
- [OpenSandbox](https://github.com/opensandbox-group/OpenSandbox) - Sandbox server you can start on Docker and later run on Kubernetes, with one lifecycle API for commands, files, and code. The README documents Python, Java, TypeScript, .NET, and Go SDKs, an osb CLI, and MCP, plus per-sandbox egress policy and a credential vault so a real secret need not sit in the workload. A Firecracker runtime with pause and resume is described for Kubernetes; published timings were not remeasured, and this list did not install the server. **Deployable platform.**
- [Vercel Sandbox](https://github.com/vercel/sandbox) - SDK and CLI for ephemeral Linux microVMs on Vercel's infrastructure. The README says each sandbox is a Firecracker microVM, that you authenticate through a linked Vercel project, and that duration defaults to five minutes, with a Hobby cap of 45 minutes and a Pro or Enterprise cap of 24 hours. You can seed a git repository, run commands, and expose ports, but there is no self-hosted server in this repository and no sandbox was started for this list. **Cloud sandbox.**
- [CubeSandbox](https://github.com/TencentCloud/CubeSandbox) - Self-hosted sandbox service, built on RustVMM and KVM, for single-node or clustered microVMs. The README says each sandbox has its own kernel, and that the project ships an E2B-compatible API, a credential vault, volumes, and automatic pause and resume, with Terraform, a Kubernetes preview, or a QEMU virtual machine when KVM is missing. The main guide asks for x86_64 Linux with KVM, and E2B compatibility plus the README's boot figures were not tested here. **Self-hosted microVM.**
- [Kubernetes Agent Sandbox](https://github.com/kubernetes-sigs/agent-sandbox) - Kubernetes controller and Sandbox custom resource for one long-lived pod with a stable hostname and optional persistent storage. The README says this is an orchestrator, not an isolation runtime: it schedules pods onto a runtime such as gVisor or Kata through a RuntimeClass you configure, and extensions add templates, a warm pool, and claims. Go and Python SDKs can reach pods through an optional HTTP router, pause and resume are documented, this is not an agent product, and no cluster was installed here. **Kubernetes controller.**
- [BoxLite](https://github.com/boxlite-ai/boxlite) - Library that runs OCI images in hardware-backed microVMs on your machine, with an optional cloud control plane the README also describes. Python, Node, Go, and Rust embeds can exec commands without a required daemon; the README says isolation uses KVM or Hypervisor.framework plus an OS sandbox, that disk state can persist, and that secret placeholders keep real values out of the guest. Egress can be limited with an allow list, a working hypervisor is required, and the cloud plane was not deployed for this list. **MicroVM runtime.**
- [Beam](https://github.com/beam-cloud/beta9) - Python API for isolated containers that run generated code, and also for GPU inference endpoints and background task queues. The README says Beta9 is the open-source engine behind Beam's hosted cloud, and that you can self-host Beta9 or use the managed service with an account and the beam-client package. A sandbox is created in code and can run a snippet remotely; the README does not document a separate export format, and this list did not self-host the engine or confirm how long a sandbox keeps its files. **Serverless platform.**
- [Celesto](https://github.com/CelestoAI/celesto) - CLI and Python SDK that give an agent a virtual machine for commands, a browser, or a desktop, on your machine or in Celesto Cloud. The README says macOS setup installs QEMU, that stop keeps files while delete removes them, that host mounts are read-only unless you mark them writable, and that outbound network is on by default. A restricted network mode is documented for Linux with Firecracker and cannot be combined with host mounts; presets cover Claude Code, Codex, and other CLIs, snapshots are described as Linux-only, and no sandbox was started here. **Local or hosted VM.**
- [OpenShell](https://github.com/NVIDIA/OpenShell) - Local gateway and CLI that start agent sandboxes and enforce a policy on files, system calls, and network connections. The README says real credentials are added only on requests to approved endpoints, and that policy changes can be held for human review after a formal check flags new access. Compute can be Docker, Podman, or host virtualization on Linux, Apple Silicon macOS, or experimental Windows WSL 2; SDKs call the gateway and do not install the CLI, a Helm install still needs your CNI to enforce NetworkPolicy, and no sandbox was created here. **Policy runtime.**
- [Coder](https://github.com/coder/coder) - Self-hosted platform for development workspaces and for AI coding agents, not only a sandbox. The README says workspaces are Terraform templates on infrastructure you choose, such as Docker, Kubernetes, or EC2, connected over a WireGuard tunnel, and that the Coder Agents loop runs in the control plane so model API keys are not placed in the workspace. Claude Code, Codex, and OpenCode are named as agents you can run in those workspaces, idle shutdown is documented, isolation is whatever the template provisions, and this list did not install a server. **Dev environment platform.**
- [Sandcastle](https://github.com/mattpocock/sandcastle) - TypeScript library that runs coding agents inside a sandbox provider and can merge their git commits back. Built-in providers are Docker, Podman, and Vercel Sandbox, and the README also ships noSandbox, which runs the agent on the host with no container; you need git plus a provider, and the scaffold expects a Claude credential in a local env file. Docker and Podman bind-mount the workspace, so Sandcastle does not add a boundary of its own, and nothing was executed for this list. **TypeScript orchestrator.**
- [Dormice](https://github.com/BitMiracle-AI/Dormice) - Self-hosted sandbox daemon with a SQLite ledger, a Docker and gVisor executor, and a lifecycle that can freeze, stop, archive, and restore sandboxes. The README says one key returns the same sandbox, that idle sandboxes cool down in place, and that the official E2B SDK can be pointed at Dormice by changing two URLs. That compatibility claim is the project's and was not tested here; the README marks the work as early development and says it is not ready for production use, and this list did not run the installer. **Self-hosted platform.**
- [Modal Sandboxes](https://modal.com/docs/guide/sandboxes) - Modal's Sandbox API starts containers for untrusted or generated code. The docs say you can select a gVisor runtime or a VM runtime, and that a sandbox stops after five minutes unless you set a timeout up to 24 hours; filesystem snapshots can preserve state past that limit. There is no public server repository, and the isolation choices are Modal's documentation, not a test run for this list. **Hosted sandbox.**
- [Sprites](https://fly.io/sprites/) - Fly.io Sprites are hosted Linux environments for agents, with a disk that survives sleep and filesystem checkpoints. The page says connectors can call external services without placing the credential inside the Sprite, and Fly describes Sprites as computers rather than sandboxes. Persistence was not exercised here. **Hosted agent computer.**
- [Deno Sandboxes](https://deno.com/deploy/sandbox) - SDK for Linux microVMs on Deno Deploy. The product FAQ says each sandbox is a Firecracker microVM with its own filesystem and network policy, and that secrets can be limited to approved hosts. Marketing claims about relative safety and about startup time are omitted and were not measured. **Hosted sandbox.**
- [Blaxel](https://blaxel.ai/) - Hosted agent runtime whose site describes a microVM per sandbox, suspend and resume, and outbound controls. The public code is SDKs, not a server you can run, and homepage boot and resume timings were not measured and are omitted. A notice that Blaxel has joined Baseten was on the homepage on 2026-09-30; that page does not say what changes for the sandbox API. **Hosted sandbox.**
- [Runloop](https://runloop.ai/) - Hosted code sandboxes for agents. The homepage describes snapshotting disk state and connecting by SSH, and it calls the environment a micro-VM plus a container; Python and TypeScript SDKs are public. The docs URL redirected and was not fully read, and homepage performance figures were not checked. **Hosted sandbox.**
- [SWE-ReX](https://github.com/SWE-agent/SWE-ReX) - Python interface that gives an agent shell sessions whose backend can be the local machine, Docker, an AWS host, Modal, or Fargate. The README says the same calls work across those backends, including interactive programs and several sessions at once, and that a Daytona extra is still work in progress. It does not document an isolation boundary, retention format, or approval step of its own; the boundary is whatever the chosen backend already provides, and the package was not installed here. **Execution interface.**
- [Sandbox Agent](https://github.com/rivet-dev/sandbox-agent) - HTTP server, meant to run inside a sandbox you already have, that controls Claude Code, Codex, OpenCode, Cursor, Amp, or Pi over a token-protected API. The README describes streaming events and permission handling, and it says the SDK does not store transcripts, so you keep the event stream yourself; embedded mode can start agents as local subprocesses, which adds no isolation boundary. The repository was last pushed on 2026-06-19 and is not archived, so that quiet stretch is not treated as abandonment, and it was not installed here. **Agent control server.**
- [AgentScope Runtime](https://github.com/agentscope-ai/agentscope-runtime) - Python runtime that deploys agent apps and runs tool calls in sandboxes for shell, Python, GUI, browser, files, or mobile. The README says you can deploy locally, on Kubernetes, or serverless, and its adapter table marks AgentScope, the Microsoft Agent Framework, and Agno as supported while LangGraph and AutoGen are only partly filled in. An archive notice says these capabilities moved into AgentScope 2.0, that this repository is read-only, and that it will be archived soon; treat that notice as the main limitation, since sandbox images were not re-checked beyond the README. **Agent runtime.**
- [OpenKruise Agents](https://github.com/openkruise/agents) - Kubernetes operator for agent sandbox lifecycle, from the OpenKruise project, with Kubernetes APIs and an E2B-style SDK. The README says it pools resources, can hibernate and checkpoint memory and disk, and routes sessions without a Kubernetes Service for every user. It also says it can use the SIG agent-sandbox APIs when those are installed, so isolation still depends on the cluster runtime underneath; E2B compatibility was not tested, and there is no standalone process documented that runs without Kubernetes. **Kubernetes operator.**

## Local and self-managed environments

- [AIO Sandbox](https://github.com/agent-infra/sandbox) - Single Docker image that exposes a shell, files, a browser with VNC, Jupyter, MCP, and a VS Code server on one shared filesystem, with Python, JavaScript, and Go clients over HTTP. The documented quick start listens on port 8080 and, without an API key, leaves those services open; the sample docker command also sets seccomp to unconfined, so bind it to localhost or a proxy. It is one container, not a kernel per task, and it was not run here. **Container environment.**
- [Anthropic Sandbox Runtime](https://github.com/anthropics/sandbox-runtime) - Command and library, srt, that applies filesystem and network rules to a process tree without giving you a virtual machine. The README says macOS uses sandbox-exec, Linux uses bubblewrap with the guest network namespace removed, and Windows uses a dedicated local user plus a firewall fence; network access is denied until you allow domains, and traffic is forced through host proxies. It is marked a research preview whose configuration may change, it does not replace the OS sandbox it calls, and it was not executed here. **Process restrictions.**
- [Microsandbox](https://github.com/superradcompany/microsandbox) - Local-first microVM runtime, with an msb CLI and Python, TypeScript, Rust, and Go SDKs, for workloads the README says should stay off the host. It runs OCI images, can fork a live sandbox, and can snapshot and restore state, including detached sessions; a sample config allow-lists outbound hosts, and the README says secret values need not enter the guest. Apple Silicon, Linux KVM, or Windows WHP is required, the project is still called beta, and no microVM was booted here. **Local VM runtime.**
- [Monty](https://github.com/pydantic/monty) - Restricted Python interpreter written in Rust, not a virtual machine and not a container. The README says filesystem, environment variables, and network do not exist inside the sandbox, and that code reaches the host only through functions and mounts you pass in. You install it as a Python, JavaScript, or Rust package; a separate commercial server, Full Monty, runs the same interpreter behind a WebSocket, snapshots and a Python subset are documented on the docs site, that limitations page was not re-read line by line, and no snippet was executed here. **Python interpreter.**
- [Agent Safehouse](https://github.com/eugene1g/agent-safehouse) - macOS command that wraps coding agents with sandbox-exec profiles and a deny-first policy. The README says default access is narrower than a full home directory, that you add the paths and integrations the agent needs, and that profiles exist for major coding agents. It is a Seatbelt hardening layer, not a virtual machine, the README says it is not a boundary against a determined attacker, Linux is outside this tool, and it was not installed here. **macOS process sandbox.**
- [Fence](https://github.com/fencesandbox/fence) - CLI that runs a command, or a coding agent, with network blocked unless a template allow-lists domains, plus filesystem and command rules you configure. The README says macOS uses sandbox-exec and Linux uses bubblewrap, and that Fence can import Claude Code permission settings and wrap Claude Code, Codex, and other CLIs. It does not add a guest kernel, a separate snapshot format is not documented, Windows is only mentioned through Nix on WSL, and Fence was not run here. **Process restrictions.**
- [CodeRunner](https://github.com/instavm/coderunner) - Local installer for Apple Silicon Macs that starts a container you can stop and resume, keeping uploads and installed packages. The README shows an MCP server, a Claude Desktop proxy, and a shell path for running Claude Code inside the container; outbound network is unrestricted unless you set the documented none mode when the container is created, and resuming cannot switch that mode. The host tool is Apple's container CLI, a hosted InstaVM product is mentioned and is not listed separately, and CodeRunner was not installed here. **Local container sandbox.**
- [Vibe](https://github.com/lynaghk/vibe) - Single binary that boots a Linux virtual machine on an Apple Silicon Mac and attaches your terminal, with the current project mounted into the guest. The README says the default template also bind-mounts several agent config directories read-write, including Claude and Codex folders, so those files are visible unless you change the mounts. The guest can reach the host at a fixed address, the host cannot reach the guest, guests cannot reach each other, the VM shuts down when you leave the shell, it needs macOS 13 or newer on ARM, and it was not launched here. **macOS VM.**
- [forkd](https://github.com/deeplethe/forkd) - Linux daemon that boots one Firecracker parent microVM and then starts child microVMs that share that parent's memory copy-on-write. The README documents a REST API and Python, TypeScript, and MCP clients, plus a branch operation that snapshots a running sandbox and resumes it. Each child is its own KVM virtual machine, but you supply the warmed parent and run the daemon on a Linux host; documented CLI examples use sudo, README spawn timings were not remeasured, and forkd was not run here. **MicroVM runtime.**
- [Shuru](https://github.com/superhq-ai/shuru) - Local microVM CLI for agents, using Apple's Virtualization framework on macOS and an experimental KVM backend on Linux ARM64. The README says each run resets the root filesystem, that network is off until you allow hosts, and that secrets stay on the host and are substituted by a proxy. Directory mounts are read-only unless you pass a read-write flag, which writes straight to the host, checkpoints can save disk state, Linux builds are marked not ready for production use, Apple Silicon is the supported Mac path, and Shuru was not run here. **Local microVM.**
- [Coi](https://github.com/coipond/coi) - CLI that starts an Incus system container, with root, systemd, and Docker inside, and runs Claude Code, Codex, or another named coding CLI there. The README says the project directory is mounted back to the host with your ownership, that SSH keys and environment variables stay out unless you forward them, and that network can be open, restricted, or allow-listed, with a profile that can keep the container between sessions. It needs Linux with Incus, macOS is documented only through Colima or Lima, this shares the host kernel, and the README's active-defense pauses were not tested. **Incus containers.**
- [Matchlock](https://github.com/jingkaihe/matchlock) - CLI and Go, Python, and TypeScript SDKs that launch ephemeral Linux microVMs for an agent command. The README says that passing an allow-host or a secret seals the network to those hosts, and that a host proxy injects the real credential so the guest only sees a placeholder. Long-lived VMs, port forwards, and volume overlays are documented and overlays are discarded when the VM goes away; it requires Linux with KVM or an Apple Silicon Mac, the README marks it experimental with breaking changes, and it was not installed here. **Local microVM.**
- [Sandlock](https://github.com/multikernel/sandlock) - Process sandbox for Linux that confines a command with Landlock, seccomp-bpf, and seccomp user notifications, without a container image or a virtual machine. The README says it needs no root, can apply a copy-on-write layer on the working directory, and can filter network by host and HTTP path; Python and Go SDKs and an OCI shim are included, and full filesystem, network, and IPC rules need Linux 6.12. The process still shares the host kernel, so this is not a guest-kernel boundary, and it was not run here. **Process sandbox.**
- [AgentBox](https://github.com/madarco/agentbox) - CLI that launches Claude Code or another coding agent in a box on your machine or on a cloud account it can log into. Locally, the command list says the box is a Docker container with a FUSE overlay, even where the introduction calls it a VM; cloud targets named in the README include Hetzner, Vercel, Daytona, E2B, and DigitalOcean. Git credentials are described as staying on the machine you start from, with a permission request before push, you need Docker and Node, the first local create builds an image, and that VM-versus-container wording was not resolved by running it. **Local or cloud boxes.**
- [Gondolin](https://github.com/earendil-works/gondolin) - Experimental TypeScript control plane that boots a local Linux microVM, QEMU by default, with an optional krun backend. The README shows host-side HTTP hooks that allow only named hosts and inject secrets for those hosts, so the guest sees a placeholder. A CLI can attach a shell, open ingress, and snapshot a session, the documented snapshot command stops the VM, filesystem modes include read-only, memory, and copy-on-write, you run the virtual machine yourself, and it was not started here. **Local microVM.**
- [LLM Sandbox](https://github.com/vndee/llm-sandbox) - Python library that runs model-written code in a container backend you already operate: Docker, Podman, or Kubernetes. The README documents sessions for Python, JavaScript, Java, C++, Go, and R, an interactive Python kernel that keeps state across calls, file copy, and an MCP server for desktop clients. Resource limits and network controls are session settings, not a separate hypervisor, so isolation is the backend's; the README does not document a hosted service or a human approval step, and the library was not installed here. **Python library.**

## Browser environments

- [Browserless](https://github.com/browserless/browserless) - Docker images that serve Chromium, Firefox, or WebKit over a WebSocket for Puppeteer or Playwright, with a hosted cloud as the other way to run the same API. The README documents a debug viewer, session replay, an MCP server for several desktop assistants, and persistent browser state with a retention setting. Your script stays in your process and the browser runs in the container or on their cloud; the README distinguishes a self-hosted image from a fuller enterprise image, isolation was not tested, and the container was not started here. **Browser environment.**
- [Steel Browser](https://github.com/steel-dev/steel-browser) - Browser API you can run in Docker or on Steel Cloud, creating sessions that Puppeteer, Playwright, or Selenium can attach to. The README says the server keeps cookies and local storage for a session, can add proxies and extensions, and ships a UI for viewing sessions plus request logs; a REST API can also return markdown, screenshots, or PDFs, and the project describes itself as a public beta. You still bring the agent logic, isolation was not tested, and the image was not run here. **Browser environment.**
- [Browserbase](https://www.browserbase.com/) - Hosted browsers for agents, with search and fetch APIs beside the browser sessions. You authenticate with an API key and the browser runs on their cloud; the site documents live view and session replay, so activity can be retained there. Stagehand, the automation SDK, is a separate project and is not listed, and isolation was not tested. **Hosted browsers.**

## Isolation building blocks

- [Firecracker](https://github.com/firecracker-microvm/firecracker) - Virtual machine monitor that uses Linux KVM to run small microVMs with a reduced device model. The README says you provide the kernel and root filesystem, then add memory, network interfaces, disks, and optional sockets yourself. It is a building block for multi-tenant container and function hosts, not an agent product, and other runtimes such as Kata integrate it; isolation also depends on the host configuration documented in their production host setup, which was not applied here. **VM building block.**
- [gVisor](https://github.com/google/gvisor) - User-space application kernel, written in Go, that implements a Linux-like interface so a container makes fewer calls into the host kernel. The README includes runsc, an OCI runtime for Docker and Kubernetes, and it says gVisor is not a seccomp filter and not a virtual machine in the everyday sense. It is a building block, not an agent product, it does not choose which files or credentials you mount in, builds target x86_64 and ARM64, and runsc was not installed here. **Container isolation.**
- [Kata Containers](https://github.com/kata-containers/kata-containers) - Container runtime that starts workloads inside lightweight virtual machines so they feel like containers but sit behind a guest kernel. The README describes a runtime that container managers launch, an agent process inside the virtual machine, and an optional built-in VMM called Dragonball; it runs on 64-bit x86, Arm, Power, and IBM Z where the matching hardware virtualization exists. Kata is a building block, not an agent product, you still choose the image, network, and mounts, and no Kata pod was started here. **VM-backed containers.**

## Contributing

Missing something useful? Read the [contribution guide](CONTRIBUTING.md) and open an issue or pull request with an official source.

The machine-readable [list.json](list.json) includes a primary-source link and a documentation-check date for every entry. Descriptions are editorial summaries of upstream documentation; inclusion does not imply hands-on testing, a security audit, or endorsement. Hosted services and source code may have different terms.

To update the list, edit `list.json`, run `bun run build`, then `bun run check`. The README is generated; avoid editing it directly.
